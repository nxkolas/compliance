# Gap Analysis Single Lifecycle and Action-Plan Lock

Status: proposed on 2026-07-23 after product review of commit `1372163`
(`feat: gap-analysis change v1`).

## Goal

Replace the repeatable Gap Analysis and reconciliation workflow with one simple
organization lifecycle:

```text
answer questions
      |
select optional documents
      |
review exact inputs
      |
generate one Gap Analysis
      |
review and manually correct findings
      |
generate one action plan
      |
Gap Analysis permanently locked
```

The Gap Analysis is generated by AI once. Its input snapshot remains visible,
but it cannot be edited or regenerated after successful generation. Findings
may be corrected manually until the action plan is created. Creating the action
plan atomically confirms the current Gap Analysis, creates the organization's
single action plan, and permanently locks the analysis.

The Documents page becomes a generic document hub. It does not display or
control Gap Analysis or action-plan relationships, although the initial Gap
Analysis can still select eligible documents from the hub.

## Confirmed Product Decisions

### Before Gap Analysis generation

- Keep the guided input sequence:
  1. **Answer questions**
  2. **Select documents**
  3. **Review information**
  4. **Gap Analysis results**
- Keep the step numbers visible. Never replace the numbers with checkmarks.
- Documents are optional.
- Users may move between the input steps and edit their answers and selection
  until generation succeeds.
- A failed or cancelled generation leaves the inputs editable and supports a
  retry using the reviewed inputs.

### After successful generation

- A successful generation permanently freezes the questionnaire and selected
  document snapshot.
- Remove **Update analysis** and all user-facing reassessment behavior.
- Do not allow a second AI-generated Gap Analysis for the organization.
- Replace the input wizard with two separate views:
  - **Gap Analysis results**, which is the default;
  - **Inputs used**, which shows the exact frozen questionnaire answers and
    document versions.
- Do not collapse **Inputs used** into the results page.
- Owners and administrators may manually correct findings while no action plan
  exists.
- Members and auditors retain their existing read-only/result permissions.

### Finding status and document support

- Finding status and organization-document support remain independent.
- `fulfilled` is valid and confirmable without an uploaded document.
- Display an amber warning icon beside **No document provided**.
- The missing-document indicator is informational. It does not downgrade the
  status, block plan generation, or create an action-plan item for an otherwise
  fulfilled finding.

### Questionnaire and AI disagreements

- Do not hardcode questionnaire-answer-to-finding-status mappings.
- Do not add per-question semantic mappings or assume that future single-select,
  multi-select, and free-text questions share one status model.
- Add a prompt-level instruction asking the model to explicitly explain when
  its finding status disagrees with the supplied questionnaire assertions.
- Display a neutral informational warning such as:
  **The generated assessment differs from your questionnaire answer.**
- Show the model's explanation with the warning.
- This warning does not create a new confirmation blocker.
- Existing contradiction and `requiresReview` behavior remains unchanged.
- Prompt-level detection is intentionally best-effort rather than
  deterministic.

### Action-plan boundary

- Remove the separate **Confirm result** action.
- Replace it with one **Generate action plan** action on the editable result.
- Before execution, show an explicit confirmation dialog explaining that:
  - the current Gap Analysis will be confirmed;
  - one action plan will be generated from it; and
  - the Gap Analysis will become permanently read-only.
- Confirmation, plan creation, item creation, audit events, and the accepted
  Gap pointer must commit in one database transaction.
- If any part fails, roll back the entire operation. The Gap Analysis remains
  unconfirmed/editable and no plan or partial plan items remain.
- Once a plan exists:
  - remove all Gap Analysis edit controls;
  - show a clear notice that plan generation locked the analysis;
  - reject correction and regeneration attempts at the server boundary.

### Action plan after creation

- An organization has at most one action plan.
- The generated set of measures is fixed.
- Do not regenerate, reconcile, automatically add, or automatically remove
  measures.
- Keep measure execution fields editable:
  - status;
  - assignee;
  - deadline;
  - notes or description fields already supported by the plan.
- Preserve audit history for changes to those fields.

### Documents hub

- Keep generic document features:
  - upload a document;
  - search;
  - processing/indexing status;
  - upload and view versions;
  - archive and show archived documents.
- Remove from the Documents page:
  - Gap Analysis evidence-selection checkboxes;
  - Gap reassessment draft controls;
  - **Prepare reassessment** and related navigation;
  - usage badges for candidate/confirmed Gap Analysis results;
  - action-plan usage badges and controls.
- Gap Analysis step 2 may still read eligible current document versions from
  the library before the one analysis is generated.

### Existing development data

- No compatibility migration is required for current local organizations.
- Development data may be cleared and reseeded with the existing NIS2 and SQL
  scripts if clean lifecycle verification requires it.
- Do not make database clearing part of normal application startup or the
  production rollout.

## Current Implementation Diagnosis

Commit `1372163` implements a repeatable four-step reassessment workflow. That
model conflicts with the lifecycle above in several places.

### Stepper completion state

`components/gap-analysis/gap-analysis-stepper.tsx` replaces a step number with a
checkmark whenever the step is before the furthest available step. Existing
results therefore show checks for prior sections. This is code-driven behavior,
not stale data from an earlier analysis.

### Reassessment remains the primary input mechanism

`components/gap-analysis/gap-analysis-workflow.tsx` exposes **Update analysis**
and uses the reassessment draft APIs to edit evidence and generate later
results. The server exposes prepare, evidence-update, generate, and retry
routes under:

```text
/api/organizations/:organizationId/gap-analysis/reassessment/*
```

The internal draft machinery can still be reused to stage the first
generation, but successful generation must become terminal and all later
reassessment entry points must be removed or rejected.

### Post-generation inputs are not guaranteed to be the pinned snapshot

`workflow-reader.ts` currently derives selected documents from the current
reassessment draft. A permanent **Inputs used** view must instead resolve:

- the assessment revision pinned by the generated Gap revision's
  `assessment_revision` source; and
- the exact `document_version` artifact sources pinned to that revision.

It must not read a mutable/latest questionnaire snapshot or whichever draft is
currently open.

### Approval and plan generation are separate transactions

`approveGapRevision` and `generateActionPlan` currently run independently:

1. `approveGapRevision` marks the revision approved and advances
   `acceptedRevisionId`;
2. `generateActionPlan` later requires that approved revision and creates the
   plan in a separate transaction.

This permits a confirmed-but-no-plan intermediate state and cannot provide the
agreed rollback behavior. Both operations must be composed into one
transactional command.

### The plan still supports reconciliation

The action-plan page detects newer accepted Gap revisions, prepares a
reconciliation, collects reconciliation decisions, and activates a replacement
plan revision. This is incompatible with a fixed single plan and should be
removed from the normal UI and API surface.

### The Documents page is coupled to Gap reassessment

The Documents page calls `gapPageReader.readDocuments` and passes an assessment
and reassessment draft into `OrganizationDocumentManager`. The component mixes
generic upload/version/archive controls with evidence selection, usage badges,
and reassessment preparation. The page needs a document-only read model and
component contract.

### Fulfilled-without-document behavior

The domain validation added by `1372163` already permits a fulfilled finding
without `document_chunk` evidence, and the focused tests pass. Preserve that
rule. The remaining change is a clearer amber informational treatment for
**No document provided**.

### AI disagreement handling

The prompt currently says that questionnaire assertions may support status and
that contradictions should be surfaced. It does not explicitly require a
non-blocking explanation when the model chooses a different status from a
questionnaire assertion.

The existing `contradictions` field cannot be reused for the new informational
warning because validation requires every non-empty contradiction list to set
`requiresReview=true`, which blocks confirmation. A separate non-blocking
metadata field is required if the warning is to be rendered distinctly.

## Target State Model

Add an explicit derived workflow mode:

```ts
type GapLifecycleMode =
  | "collecting_inputs"
  | "generating"
  | "generated_editable"
  | "locked_by_action_plan";
```

Derive it from authoritative stored state:

| Mode | Condition | Allowed UI |
| --- | --- | --- |
| `collecting_inputs` | No successfully generated Gap revision | Input wizard |
| `generating` | First generation job is active | Frozen review/progress |
| `generated_editable` | Gap revision exists and no action plan exists | Results, inputs used, manual finding corrections |
| `locked_by_action_plan` | Active action plan exists | Read-only results and inputs used |

A failed or cancelled first-generation job returns to `collecting_inputs`.

The active action plan is the authoritative lock marker. No new mutable
client-side lock flag should be trusted. A database column is unnecessary
unless implementation reveals that an active-plan existence check cannot
express an invariant.

## Server-Side Invariants

Enforce the lifecycle in services and routes, not only by hiding buttons.

1. An organization with a successful Gap revision cannot submit a new
   questionnaire snapshot for Gap generation.
2. It cannot change the selected evidence set or start another generation.
3. An organization with an active action plan cannot correct a Gap finding.
4. It cannot approve a Gap revision through the old standalone approval route.
5. It cannot create a second action plan.
6. The combined finalization command only accepts the current Gap revision.
7. Existing coverage, citation, stale-current, permission, and unresolved
   contradiction checks still apply.
8. Concurrent correction and plan-generation requests serialize on the same
   organization Gap artifact. The loser receives a stable conflict response.

Suggested stable error codes:

```text
GAP_ALREADY_GENERATED
GAP_INPUTS_LOCKED
GAP_LOCKED_BY_ACTION_PLAN
GAP_REVISION_NOT_CURRENT
ACTION_PLAN_ALREADY_EXISTS
GAP_FINALIZATION_FAILED
```

### Phase 7: Implement atomic finalization and plan generation

Create one application service, for example:

```ts
finalizeGapAnalysisAndGenerateActionPlan({
  userId,
  organizationId,
  gapRevisionId,
  locale,
})
```

Within one database transaction:

1. acquire a row lock on the organization's Gap artifact;
2. verify the submitted revision is still current;
3. verify no active action plan exists;
4. load and validate the pinned release, applicability outcome, complete
   finding coverage, citations, stale-current state, and existing review
   blockers;
5. build the plan baseline from all non-fulfilled findings;
6. mark the Gap revision approved;
7. advance the artifact's `acceptedRevisionId`;
8. insert the one active action plan;
9. insert all baseline plan items;
10. insert Gap-approval and action-plan-generation audit events;
11. return the created plan and locked Gap state.

Refactor the existing approval and plan-generation logic into helpers that
accept the same transaction executor. Do not call two public services that each
open their own transaction.

Both finalization and manual correction must lock/check the same artifact row
so plan creation cannot race with a final correction. Idempotent replay should
return the already-created plan only for the same command key and fingerprint;
an unrelated second request receives `ACTION_PLAN_ALREADY_EXISTS`.

Update the action-plan generation request contract to accept the current Gap
revision rather than an already-approved revision.

Remove or disable the standalone Gap approval endpoint and client action.

## Automated Acceptance Matrix

### Workflow state

- New organization sees the numbered input wizard.
- Completed input steps retain their numbers rather than checkmarks.
- Failed generation returns to editable inputs.
- Successful generation defaults to results.
- **Inputs used** is a separate read-only view.
- Successful generation removes all reassessment/update actions.
- Direct URLs and API calls cannot start a second generation.

### Frozen inputs

- The displayed answers come from the assessment revision pinned to the Gap
  result.
- The displayed documents are the exact pinned versions.
- Uploading a later document version does not alter **Inputs used**.
- Archiving a pinned document does not erase it from the snapshot.
- Zero selected documents renders a clear empty state.

### Findings

- AI and manual findings may be fulfilled without a document.
- Missing documents show an accessible amber indicator.
- Missing documents do not block finalization.
- Prompt-produced questionnaire disagreements render informationally.
- Questionnaire disagreements do not create `requiresReview`.
- Existing true contradictions still block finalization.
- Manual corrections work before plan creation.
- Manual corrections fail after plan creation.

### Atomic plan generation

- The command accepts only the current Gap revision.
- Success approves and accepts the revision, creates exactly one plan, creates
  the expected non-fulfilled items, and locks the Gap.
- A failure before plan insertion leaves the Gap unapproved.
- A failure during item insertion removes the plan and rolls back Gap approval.
- A failure during audit insertion rolls back all earlier writes.
- Replaying the same idempotency key returns the same plan.
- A different second request cannot create a second plan.
- Concurrent correction and generation cannot both commit.

### Locked state

- Results and frozen inputs remain readable.
- Edit controls are absent.
- A plain-language lock notice is visible.
- Direct correction, questionnaire, evidence, generation, and standalone
  approval requests are rejected.

### Action plan

- One fixed measure set is generated.
- No reconciliation or refresh controls are visible.
- No route can generate a replacement plan.
- Status, assignee, deadline, and supported notes remain editable.
- Item edit concurrency and audit behavior still work.

### Documents hub

- Upload, search, processing state, versions, and archive still work.
- No Gap selection, reassessment, candidate/confirmed-result usage, or
  action-plan usage controls appear on the Documents page.
- Gap step 2 can still select eligible documents before generation.

## Definition of Done

The change is complete when:

- each organization can successfully generate only one AI Gap Analysis;
- the exact generated inputs remain available in a separate read-only view;
- no reassessment/update path remains reachable;
- findings remain manually editable until plan creation;
- fulfilled findings without documents remain valid and visibly distinguish
  status from support;
- AI/questionnaire disagreements are explained without hardcoded mappings or
  new blockers;
- one atomic command confirms the result, creates the one action plan, and
  locks the Gap Analysis;
- failure cannot leave a partially confirmed result or partial plan;
- the plan's measure set is fixed while execution fields remain editable;
- the Documents page is a generic hub without Gap/action-plan workflow
  controls;
- server guards enforce every lock independently of the UI;
- German and English are updated together; and
- lint, typecheck, tests, AI evaluations, build, and manual QA pass.
